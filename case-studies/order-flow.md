# 주문 흐름 설계

## 문제

전화 주문에서는 고객 주소를 통화나 문자로 다시 전달받고 판매자가 이를 택배 업무에 재입력해야 합니다. 같은 정보가 여러 사람과 시스템을 거치면서 누락, 오입력, 상태 불일치가 발생할 수 있습니다.

## 설계 목표

- 고객이 자신의 배송지를 직접 입력하도록 한다.
- 신규 고객과 재주문 고객의 흐름을 모두 지원한다.
- 주문 등록, 택배 접수, 취소, 배송 상태를 하나의 생명주기로 관리한다.
- 화면이 아닌 백엔드 정책에서 허용 가능한 상태 변경을 결정한다.
- 판매자, 구매자, 택배기사의 행동이 서로 충돌하지 않도록 한다.

## 구현 흐름

```text
1. 판매자가 고객 전화번호로 일회성 주문 링크 발송
2. 구매자가 본인 확인 후 배송 정보 입력
3. 기존 고객은 최근 배송지 재사용 또는 새 주소 등록
4. 판매자 앱으로 주문 전달 및 Push 알림
5. 판매자가 택배 접수 또는 취소
6. 송장 생성·출력 및 배송 상태 Webhook 반영
```

## 주요 판단

### 일회성 주문 링크

고객에게 판매자용 기능이나 내부 식별자를 노출하지 않고 해당 주문 요청에 필요한 범위만 허용했습니다. 만료·취소된 요청은 재사용하지 못하도록 상태 충돌을 처리했습니다.

### 주소 재사용

이전 주문 주소를 단순 복사하지 않고 주소록 식별자와 원본 주문 관계를 구분했습니다. 고객이 수정하거나 새 주소를 등록해도 과거 주문의 배송 정보가 변경되지 않도록 책임을 분리했습니다.

### 상태 정책

주문 접수, 택배 접수, 취소, 배송 완료 상태에서 가능한 행동을 서비스 정책으로 분리했습니다. 사용자 역할과 현재 상태를 함께 확인하고 잘못된 순서의 요청은 충돌 응답으로 차단했습니다.

## 예외 상황

- 링크 발송 후 판매자가 요청을 취소한 경우
- 고객이 여러 브라우저에서 동시에 제출한 경우
- 기존 주소를 불러온 뒤 새로운 주소로 변경한 경우
- 택배 접수 도중 외부 API가 실패한 경우
- 판매자 또는 택배기사 계정 상태가 변경된 경우
- 배송 Webhook이 중복 수신된 경우

## 검증

주문 상태 매핑, 취소 정책, 배송지 변경 정책, 판매자·기사 계정 상태, 외부 택배 등록 상태를 단위 테스트로 검증했습니다. 외부 연동과 DB 상태 변경의 경계를 분리해 실패 지점을 재현할 수 있도록 구성했습니다.

## 결과

주소 요청 → 주문 등록 → 택배 접수 → 송장 출력 → 배송 확인이 하나의 서비스 흐름으로 연결되었습니다. 사용자는 역할별로 필요한 화면만 사용하고 상태 일관성은 백엔드에서 관리합니다.
