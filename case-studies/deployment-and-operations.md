# 배포와 운영 설계

## 목표

- 데이터베이스 스키마와 애플리케이션 버전의 불일치를 방지한다.
- 새 버전이 준비되지 않은 상태에서 운영 컨테이너를 먼저 중단하지 않는다.
- 배포 실패 시 이전 이미지로 복구할 수 있어야 한다.
- 한 요청을 Gateway부터 각 백엔드 서비스까지 추적할 수 있어야 한다.
- 외부 API의 일시적인 장애가 데이터 유실로 이어지지 않게 한다.

## 배포 순서

```text
1. 대상 API 이미지 전체 선빌드
2. Flyway 마이그레이션 1회 실행
3. 서비스 순차 교체
4. /actuator/health 검증
5. 실패 시 직전 이미지로 롤백
```

이미지 빌드와 DB 마이그레이션이 성공하기 전에 실행 중인 서비스를 교체하지 않습니다. 스키마 호환성이 깨지는 변경은 유지보수 절차로 분리하고 자동 롤백 대신 DB 백업 복구를 전제로 처리합니다.

## 데이터베이스 변경

- Flyway 버전으로 변경 이력 관리
- 운영 애플리케이션은 스키마 자동 변경을 사용하지 않고 validate만 수행
- 이미 적용된 migration 파일의 수정·삭제 금지
- 실패한 migration의 자동 repair를 일반 배포에서 수행하지 않음
- 파괴적 변경은 별도 maintenance 명령으로만 실행

## 요청 추적

Gateway가 안전한 `X-Request-ID`를 생성하거나 전달합니다. 각 백엔드 서비스는 동일한 값을 로그 MDC에 포함해 서비스 간 호출을 하나의 ID로 추적할 수 있습니다.

```text
Client → Gateway → Seller API → Order API
           └──── same Request ID ────┘
```

입력된 ID가 없거나 허용하지 않는 형식이면 UUID를 새로 생성합니다. 응답 헤더에도 Request ID를 포함해 운영 문의와 서버 로그를 연결할 수 있도록 했습니다.

## 외부 연동 복구

- Push와 알림은 Outbox에 저장 후 비동기로 처리
- 실패한 작업은 재시도 횟수와 다음 실행 시간을 기록
- 외부 택배 계약·접수 동기화 실패를 복구 스케줄러가 재처리
- 배송 Webhook 중복 수신을 식별해 멱등 처리
- 장시간 진행 중 상태로 남은 작업을 별도 복구 대상으로 분류

## 운영 안전 장치

- Caddy에서 TLS 종료 및 공개 도메인 라우팅
- 서비스 포트는 loopback 또는 내부 네트워크에만 노출
- 내부 API는 별도 인증 필터로 보호
- 관리자 로그인, SMS, 주소 검색에 호출 제한 적용
- 개인정보 암호화 키와 DB 스키마 상태를 시작 시 검증
- 로그 파일 크기·보관 기간 제한
- 송장 PDF 보관 기간 이후 참조와 파일 정리

## 결과

배포, DB 변경, 외부 연동 실패, 로그 추적을 기능 외부의 수작업으로 남기지 않고 코드와 운영 절차에 포함했습니다. 장애가 발생했을 때 실패 지점을 확인하고 안전한 복구 경로를 선택할 수 있는 구조를 만들었습니다.
